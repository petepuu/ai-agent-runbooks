# Build Prompt 2 — Agent, Workflows and Integrations

Use this prompt **after** the **Copilot License Lifecycle** solution and Dataverse
tables from Power Apps Plans are saved and verified. Paste
it into the natural-language builder on the
[Copilot Studio home page](https://copilotstudio.microsoft.com/), not into an
agent's end-user chat or its global Instructions field.

The builder can create agents, deterministic workflows or a combination, and may
ask for connections. This does **not** establish that it can deploy an external
MCP server, grant Entra consent, implement atomic backend transactions or create
every approval adapter. The prompt asks it to create what the surface supports
and return precise implementation handoffs for the rest, without claiming a
complete working deployment.

## Supply this context

Paste the verified **Dataverse schema handoff** captured from the saved tables
using [Prompt 1's checklist](1.Dataverse.md#schema-handoff-for-stage-2).
For this integration stage, also supply the environment ID/URL, solution unique
name, publisher prefix and preferred-solution status from the maker portal,
plus auditing, concurrency and
role-configuration status. Verify the 26 base columns and five approved lookups
(31 custom columns), including relationship requiredness and delete behavior.
Supply the
following documents as readable context, by pasting their contents or attaching
them if that surface supports attachments:

| Context | Purpose |
|---|---|
| [Capability matrix](../Capability-matrix.md) | Minimal schema boundaries, exact tool schemas, action boundaries, approval and failure contracts |
| [Runbook](../../3.Runbook.md) | Agent-wide instructions, backend jobs, setup and release gates |

Local repository paths in this document are navigation for the maker, not proof
that the Studio builder can read those files. If the builder cannot consume a
document or import a skill, supply the content or perform the documented upload
manually. Never replace missing contracts with guessed operations.

## Copy-ready prompt

```text
Build the agent, deterministic workflows and integration wiring for
Copilot Licence Lifecycle Agent in Microsoft Copilot Studio, using the
GitHub Copilot harness.

This is a BUILD request, not just an architecture discussion. Create supported
artifacts as drafts in my development environment and show their actual artifact
references. Do not publish, enable schedules, send live messages, change live
licences or run write-capable tests against production.
If an item requires another surface or custom code, return its exact implementation
contract, dependencies, owner and completion check. Do not represent a stub,
generated plan or unattached connector as a working implementation.

INPUTS AND PRECONDITIONS
Use the verified solution and Dataverse schema handoff from Power Apps Plans.
Reuse the unmanaged solution with display name Copilot License Lifecycle and
the actual unique name from that handoff; never infer it from display name alone.
If the solution is missing, ask before creating it.
Do not create a duplicate solution or a model-driven application.
Reuse these five tables, their 26 base columns and five approved lookup columns
from Architecture (31 custom columns),
using actual logical names, choice values and native keys:
LicenseHolder, WaitlistEntry, ReclaimCase, Configuration, AuditEvent.
Do not add other custom columns, relationships, alternate keys or tables.
The minimal tables do not supply a durable operation/approval/history store.
Do not hide an expanded control schema inside AuditEvent.Details.
Do not recreate/rename tables, guess entity set names or create a second solution.
Confirm environment ID and solution unique name against the handoff.
Verify the maker's preferred solution, and explicitly bind the agent and supported
solution-aware components to this solution. Preferred solution alone does not
configure every component, connection or Copilot Studio agent.
If the handoff is missing, Proposed, mismatched or incomplete, request the missing
metadata and stop dependent wiring. Preserve any completed safe draft work.
If an existing environment uses a different schema, request a separate reviewed
migration plan; do not delete tables or reinterpret their stored data.

Use the supplied Capability-matrix, Runbook, Sample-prompts, Resources and ten
runtime skill files as the implementation specification. Confirm which you can
actually read. Do not assume access to my repository from a filename or URL.
If a required document is inaccessible, ask for its contents before building that
part. Keep actual deployment values and credentials out of generated instructions.

STANDARD SOLUTION
Create one agent named exactly Copilot Licence Lifecycle Agent.
Use instructions for global policy, skills for task procedures, and narrow tools
for operations. No second agent, generic directory administration tool, native
email agent channel or indexed knowledge source is required.

Include all ten capabilities:
1. copilot-licence-inventory: inventory, capacity and known assignment dates.
2. copilot-usage-insight: activity, dormancy, trends and reclaim history.
3. copilot-waitlist-status: ordered queue, request status and historical waits.
4. copilot-waitlist-intake: create a PendingApproval request.
5. copilot-waitlist-review: approve, reject or policy-authorized reprioritization.
6. copilot-dormancy-notify: confirmed bounded warnings and reminders.
7. copilot-licence-reclaim: approved removal of eligible direct assignments.
8. copilot-licence-assign: separately approved queue-head allocation and notice.
9. copilot-reclaim-cancel: cancel an open case without reversing a removal.
10. copilot-reclaim-dispute: record and route a dispute without auto-restoration.

The licence management team are the direct users. Department managers and
employees participate through the existing request/contact routes and receive
scoped updates, not estate-wide activity access.
Intended published channels are authenticated Teams and Microsoft 365 Copilot,
enabled only after separate channel tests and release approval.

IMPLEMENT IN DEPENDENCY ORDER

A. BIND THE EXISTING DATA MODEL
Map every business alias to the verified Dataverse metadata before generating
queries or updates. EntryId and CaseId are the native business-table keys.
Proposal, operation, approval and snapshot references come from the relevant
approved backend components, not invented columns or assumed AuditEvent IDs.
Map API case status to ReclaimCase.Outcome and queue status to WaitlistEntry.Status.
Use ReclaimCase.LicenseHolder and ReclaimCase.Configuration as required lookups.
Use AuditEvent.LicenseHolder, AuditEvent.WaitlistEntry and AuditEvent.ReclaimCase
as optional lookups. Verify Restrict Delete and no other supported cascading.
Keep the existing text identifiers unchanged. A case's UserId must match its
holder. Validate consistent targets when an audit event links multiple records.
Waitlist intake must work without a holder record.
For case detection, bind the verified holder and the selected approved settings
row. Keep referenced settings unchanged; new settings use a new row selected
through approved deployment configuration. Do not guess missing historical links.
For assignment, link audit to the fulfilled request and resulting holder;
for case actions, link audit to the case and holder. Job-only audits need no
target lookup. Include links with the related transactional state/audit writes.
Use native ETags, not editable version fields. Order approved entries by Position,
then RequestedOn and native entry ID. Missing/invalid positions hold allocation.
Reordering updates Position under authorized policy, with concurrency protection.
Bind one tenant/Copilot SKU per deployment from authenticated integration settings,
not extra row columns. Other action/evidence fields in tool contracts are
integration data, not instructions to expand the Dataverse schema.
Keep AuditEvent to Timestamp, Actor, Action, TargetUser and Details.
An audit description is not a trusted receipt or an idempotency guarantee.
Use verified history only when an approved integration provides it; otherwise
return a history gap, never a trend from the current holder record.
Identify existing approved components for immutable proposals, trusted approvals,
idempotency, reservations and per-channel receipts. If absent, return concrete
design/implementation blockers and leave dependent live tools disabled.
Any new storage design needs separate approval; do not create it implicitly.
Record environment-specific values in configuration/environment variables and
use supported connection references; keep secrets in approved secret storage.

B. IMPLEMENT THE AUTHENTICATED OPERATION BOUNDARY
Retain the scoped MCP facade described in the supplied design.
Expose only these thirteen exact tool contracts:
lifecycle_inventory, lifecycle_usage, lifecycle_waitlist, lifecycle_context,
lifecycle_prepare, lifecycle_status, lifecycle_waitlist_add,
lifecycle_waitlist_review, lifecycle_notify, lifecycle_reclaim,
lifecycle_assign, lifecycle_cancel, lifecycle_dispute.

Use the input/output schemas and allowed fields in Capability-matrix.
For reads return status, sourceIds, asOfUtc, complete, gaps and pagination;
usage also includes refresh date, coverage and identity-mapping state.
Prepare stores the exact normalized payload, hash, policy/row versions and
expiry, and returns a proposal plus authenticated approval reference.
The seven execute tools accept only proposalId, approvalId and idempotencyKey.
Load the actual prepared payload server-side, never a second mutable payload.
Status returns per-target/per-step evidence without secretly re-executing.

Authenticate the caller and enforce current tenant, licence-team/action role,
SKU allowlist and operation enablement in deterministic backend code.
Never accept an actorId or approved=true from the model as authority.
Capture explicit human confirmation using a trusted approval adapter bound to
the exact proposal/hash/expiry. If the channel cannot authenticate a confirmation
event, use a real authenticated approval surface and returned reference.
Never fabricate an approval link. Keep verified decisions immutable and keep
the executor from manufacturing approval records.
Never treat an AuditEvent row, its Action text or its Details as authentication.
The approved adapter must supply independently verifiable receipts. If no durable
receipt/operation implementation is available, report the blocker rather than
adding columns or bypassing confirmation.

Enforce <=25 distinct targets in prepare AND execute. Never automatically split
and run oversized requests. Use stable operation keys, version checks, atomic
active-case/queue uniqueness and reservation/transition logic.
Do not replace these with "List rows, then create" race-prone logic or a prompt.
Dataverse ETags do not make Graph and Dataverse one transaction.
Persist intent and step results, reconcile uncertain external effects and
preserve successful partial work.

If this builder cannot implement/host the MCP facade, authentication bridge,
approval adapter or transactional backend, say so explicitly. Produce the exact
external work items and leave their dependent live tools blocked. Do not attach
unrestricted Graph/Dataverse actions as a shortcut or silently switch architecture.
Create other supported draft components without pretending these dependencies
are finished.

C. CREATE FIVE LIFECYCLE WORKFLOWS
Preserve deterministic backend logic. Use the supported workflow authoring
surface and record the actual engine, trigger and integration route.
The supplied design uses solution-aware Power Automate backend flows. If this
builder can only create GHCP Workflows drafts, identify them as such and prove
their secure backend/MCP invocation and ALM route before substitution. Do not
claim they are Power Automate exports or imply automatic transport parity.

1. Sync licence inventory
   Daily scheduled definition, inactive during build.
   Read all directory pages and subscribedSkus; select only approved Copilot
   SKUs. Retrieve the current documented v1.0 Copilot usage CSV:
   GET /v1.0/copilot/reports/getMicrosoft365CopilotUsageUserDetail(period='D90')
   when D90 covers the configured threshold. Pin/test report version and headers.
   Resolve authorized identities, classify mapping gaps and update only the
   listed holder columns. Return report metadata through the read adapter.
   Use approved retained evidence when available; otherwise report missing
   history. Never convert null/missing/anonymized usage to zero activity.

2. Detect dormancy
   Weekly scheduled definition, inactive during build.
   Read the owner-approved settings, complete fresh evidence and exclusions.
   Compute full observed UTC days. Create one open eligible case per holder/SKU
   transactionally, populate the required holder/configuration lookups, record
   policy/evidence and linked audit, and do NOT notify or reclaim.
   Exclude direct-action-ineligible inherited/mixed assignments and unknowns.

3. Notify
   Authenticated on-demand campaign preparation/execution plus scheduled resume
   of an already approved bounded campaign. No autonomous approval creation.
   Bind exact <=25 recipients, initial content, both Teams/Outlook channels,
   template version, grace rule and reminder offsets.
   Recheck evidence/exclusions/case state before each send. Suppress work for
   cancelled, disputed or reactivated holders. Start grace only after both
   initial notices are accepted; acceptance is not guaranteed delivery.
   Track both channels and each reminder separately. Hold bounces, required
   reminder failures and unknown sends. Reconcile before resending.

4. Reclaim
   Authenticated action, no automatic scheduled removal.
   Require exact unexpired verified human approval, completed notices/reminders,
   elapsed grace, no dispute/exclusion, current direct-only entitlement and
   complete fresh usage covering grace end.
   Recheck immediately before Graph mutation. Remove only the allowed SKU using
   POST /v1.0/users/{id}/assignLicense with addLicenses=[] and
   removeLicenses containing only that SKU.
   Verify effective state and persist case/audit. Reconcile Graph success with
   Dataverse failure before any dependent assignment. No group edits.

5. Assign from waitlist
   Authenticated action with a NEW assignment approval, not reclaim approval.
   Resolve the next approved eligible request, exact user/SKU and included
   confirmation notice. Reserve queue/capacity and recheck current entitlement,
   prerequisites, usage location and policy/row versions.
   Add only that SKU through assignLicense with removeLicenses=[].
   Verify effective assignment, set Status=Fulfilled and record the action time
   in AuditEvent.Timestamp with holder and waitlist lookups, then send the approved
   notice. A changed head requires new confirmation.
   Assignment success plus notice failure is partial completion; recover the
   notice, not the assignment.

Do not invoke the agent from these schedules merely to execute fixed rules.
The agent calls scoped tools in administrator conversations. Approved campaign
reminders need no new approval while their original bounded approval is valid.

D. IMPLEMENT SUPPORTING HANDLERS
Create/wire handlers for all read tools and context/prepare/status operations.
Add waitlist intake/review, case cancellation and dispute recording/routing:
- intake creates PendingApproval only, after duplicate and request validation;
- review enforces reviewer role, permitted transition/position and reason;
- cancellation suppresses pending work but never reverses completed removal;
- disputes retain the verified request and minimal reason, hold future removal
  where possible and route only to the configured escalation owner.
Preserve already completed/in-flight licence outcomes during cancellation/dispute.
Persist disputes as linked operation/audit evidence, including routing results.
Use the same approval, idempotency, audit and status contracts as lifecycle writes.

E. CONFIGURE CONNECTIONS AND RUNTIME VALUES
Use the approved identities: read service principal for directory/SKU/usage,
separate owned licence-write principal, scoped Dataverse application roles,
and tested connector-supported Teams/Outlook identities.
Request maker/admin connection setup and consent where required. Do not invent
credentials or assume the current maker is the intended production executor.
Verify Graph application permissions as applicable: User.Read.All,
LicenseAssignment.Read.All, Reports.Read.All, LicenseAssignment.ReadWrite.All.
Review exclusion-group permissions separately. Verify target-cloud API support,
SKU mapping, sender/poster rights and actual connector operation IDs.
Only one trusted approval adapter may create verified approval decisions.

Keep AutoReclaimEnabled=false. Never activate policy from examples alone.
Propose 45-day dormancy, 14-day grace and day-10 reminder only as values for the
policy owner to approve. Maximum evidence age, groups, SKU IDs, queue policy,
escalation route and templates must be supplied and signed off.
Configuration has only DormancyDays, GracePeriodDays, AutoReclaimEnabled and
ExclusionGroup. Resolve the active settings and their owner approval/revision
through the approved deployment process, not added status/version columns.
Initial unpublished/inactive artifacts are a deployment safeguard, not removal
of any standard capability.

F. CREATE AND CONFIGURE THE AGENT
Name: Copilot Licence Lifecycle Agent. Harness: GitHub Copilot in Copilot Studio.
Use the complete global instructions supplied in Runbook Phase 4.
They must enforce evidence dates/gaps, no unsupported inactivity explanations,
licence-team privacy, exact confirmations, no automatic >25 splitting, separate
assignment approval, no group edits, no policy changes and honest action status.

Attach only the implemented narrow MCP server and inspect all exposed tools.
No unrestricted mail sender, Graph writer or general Dataverse updater.
Upload the ten supplied SKILL.md files in their index order via Build > Skills.
Preserve YAML names and quoted descriptions. If direct import is unavailable,
give the maker the exact pending upload list; do not claim imports occurred.
Do not paste the builder prompt into the runtime instructions or invent skills
instead of reading the supplied definitions.
No indexed knowledge is required: tools provide authoritative structured data.
Do not upload employee usage spreadsheets as knowledge.
Set starters for inventory, usage/unknowns, approved waitlist and eligible cases.
Restrict access to the licence team and do not enable cross-user personal memory.

G. VERIFY WITHOUT LIVE SIDE EFFECTS
Use the supplied synthetic fixtures in isolated adapters/connections.
Run each positive and boundary case T01-T10 and the composed reclaim/assignment
sequence where tools support safe execution. Otherwise mark them Not run.
Never present expected output as a successful test.
Check exact counts, 44/45-day threshold, 72-hour freshness edge, grace boundary,
25/26-target limit, non-maker attribution, denied/revoked identities, changed
payload/queue head, direct/inherited provenance, null/stale evidence, duplicates,
concurrency, pending/unknown and Graph/Dataverse/notification partial outcomes.
Assert five tables with the original 26 columns plus the five approved lookups,
no other custom fields. Test waitlist intake without a holder, missing/mismatched
case links, consistent audit targets and restricted parent deletion.
Missing approval/idempotency/notification infrastructure
must block dependent actions, not trigger schema expansion. Missing retained
history yields a gap; an audit description never counts as approval.
Test changed queue positions, concurrent allocations and preserved case Outcome
after failed operations. Unimplemented controls mean Blocked, not best-effort.
Use Preview and Evaluate with the right version/test identity. General quality
scores do not replace exact backend assertions.
Check both intended channels only in an explicitly approved isolated pilot.

H. RETURN THE BUILD HANDOFF
Show:
- actual agent and workflow artifact references, engine, version, solution and
  draft/publish state;
- actual five-table/31-column mappings and five relationships used, never guessed;
  explicit integration storage, approval and recovery dependencies and blockers;
- all thirteen tools: implemented/connected/tested/blocked status and dependency;
- all ten skills: imported or pending manual upload;
- each connection, identity, permission and approval adapter readiness;
- scheduled definitions and confirmation that no live schedules/actions ran;
- tests actually run with evidence, and remaining Not run cases;
- exact remaining work per owner, including external hosting/code/consent;
- release gates G1-G8 and rollback/pause procedure.

For unsupported items, use Blocked or Manual setup required, not Completed.
If only drafts/plans could be created, say that explicitly.
Keep the complete standard design in scope, but do not publish, activate schedules
or perform live licence/message actions until I separately authorize release
after the required gates pass.
```

## What the maker should receive

The result should be a draft build with a component-by-component status report,
not a claim that two build stages bypass configuration or security work. In particular,
a missing external MCP/backend implementation remains a concrete blocker to the
whole solution becoming operational.

Verify the schema handoff, tool names, approval integration and actual generated
artifacts against [the runbook](../../3.Runbook.md). Keep connector consent,
trusted confirmation capture, atomic transaction logic and production publication
as explicit human-owned checks, not model promises.
