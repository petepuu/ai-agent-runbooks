# Sample Prompts — HR Onboarding Agent

These are acceptance cases, **not evidence of successful live tests**. All tenant and integration runs are not run. Use synthetic test content in an isolated source and never replace real HR policy with these fixtures.

## How to Use These Prompts

Use the prompts in Studio Preview first, then the authenticated Teams / Microsoft 365 Copilot pilot after channel validation. Test established employees as well as new hires. Both skills and both entry paths belong to the standard scenario: chat answers questions, builds onboarding checklists and handles follow-up questions naturally; authenticated Workflows intake prepares structured results for automatic policy-authorized replies. Email tests start with isolated non-sending mocks, followed by a release-authorized real-mail pilot after setup and invocation checks.

Adapt applicability details such as cohort, country and timeframe without adding sensitive employee data. These short starter prompts are also suitable for the agent's suggested-prompts list:

- What does the approved employee handbook say about the code of conduct? Include sources.
- Make a first-week onboarding checklist from the applicable onboarding guidance.
- Summarize the available medical plans in a table; mark costs the sources do not specify.
- What supporting documents does that policy require?
- I have worked here for five years. What is the published leave-request process?

## Category 7: Email Trigger Prompts

**Autonomous user-mailbox replies are part of the standard scenario.** In chat, ask HR questions and continue the conversation normally; pasted email text does not authenticate an email event. In isolated workflow tests, supply authenticated mock intake and replace send/queue side effects with test doubles. Do not email a guessed trigger address. After E1-E2/D3 and release-level pilot authorization, use the actual connected user mailbox configured in the workflow. Routine authorized inquiries must not require a per-message approval click.

| # | Email Subject (suggested) | Email Body (Prompt) |
|---|---|---|
| 33 | Wellness benefits | What wellness benefits are documented for my cohort? |
| 34 | Medical plan inquiry | Compare the available medical plans and mark any unspecified costs. |
| 35 | Onboarding checklist | What are the first-week onboarding steps from the approved guidance? |
| 36 | Leave policy | What is the published leave-request process? |
| 37 | Travel expense | Which documents are required for travel reimbursement? |
| 38 | Code of conduct | Summarize the applicable code of conduct with sources. |

### Example Email Interaction

> **Synthetic inquiry:** Subject "First week and wellness"; body asks for week-one tasks and wellness paperwork.  
> **Interactive chat expected result:** A natural answer with cited week-one tasks and wellness paperwork, with follow-up questions only where needed; no email subject, sign-off, draft label or workflow JSON.<br>
> **Authenticated workflow expected result:** Trusted intake invokes the same published **HR Onboarding Agent**, whose HTML email is independently validated against current policy, recipient rights and source evidence. The answer includes numbered citations, all source links in a references table, and a closing greeting from HR Onboarding Agent. The backend issues payload-bound authorization and submits once **without per-message human approval**. Report only observed pending/sent/failed/unknown state. A held inquiry produces no reply and a confirmed HR queue record or visible failed handoff.

## Tips for Getting Better Responses

| Tip | Example |
|---|---|
| Provide only relevant applicability | "For cohort A, summarize the wellness policy." |
| Request an evidence-based format | "Use a table and mark information the sources do not specify." |
| Name the timeframe | "Make a first-week checklist; do not create tasks." |
| Continue the conversation | "Which supporting documents do I need for that benefit?" |
| Ask for the source of a claim | "Which current article supports that condition?" |

## Out-of-Scope Topics

Personal HR records, personal medical data, live leave balances, payroll/bank changes, benefit enrollment, leave submissions, HR case creation, provisioning, scheduling and task completion are excluded. General published benefits information is not a personal medical record. Arbitrary-recipient mail, Reply All, attachments, forwarding and autonomous replies outside the release-approved routine policy are excluded.

For unsupported questions, the expected response is an explicit evidence/scope limitation and the verified HR route when available. Do not invent a contact or claim a handoff occurred. Neither access denial nor an operator's maintenance pause can be overridden by a prompt.

### Composed Scenario

**Chat request:** "For cohort A, explain wellness paperwork and make my first-week checklist." Then ask: "What do I need to keep for the reimbursement?"

Expected **interactive chat** evidence/action sequence:

1. Confirm both standard skills are imported and the request arrived through interactive chat. Reuse cohort A, no unnecessary identity or medical questions.
2. Following global instructions, the agent retrieves F2 from configured knowledge for the current permitted caller without invoking a policy skill. Explain the receipt and short purpose statement; include the actual retrieved citation.
3. `hr-onboarding-checklist` retrieves F1 and emits exactly the three supported tasks with day/week timing and citation. Status is guidance, not completed.
4. Following global instructions, answer the follow-up using cohort A and the wellness context already established. Use applicable evidence from this task or retrieve it again when necessary. Explain the receipt and short purpose statement with citations; no email subject, sign-off, draft label or workflow JSON.
5. End with no sending. Trace contains **zero** mailbox/backend calls. The autonomous entry path is part of the same configuration, but this remains a normal chat conversation.

Expected **authenticated workflow composed sequence**, using M1 to exercise policy, onboarding and reply preparation, then M2 for ordinary established-employee guidance:

1. Mock intake first, or the qualified Outlook user-mailbox trigger in the release-authorized pilot, calls `AcceptHrEmailEvent`. Verify internal sender mapping, stable message identity, exact recipient binding, safe population/corpus and deterministic request match. Return the authoritative envelope and allowed topics and no existing reply.
2. Workflows invokes the existing published **HR Onboarding Agent** through the qualified Agent node, not through an agent-called workflow tool. Verify the target/version and effective identity. The agent uses permitted F2 policy evidence and F1 checklist evidence for M1, or F2/F6 policy evidence for M2. It must not retrieve broader service-identity content.
3. `hr-email-reply` returns a version 2 result containing a grounded HTML email, all source links in a references table and an agent sign-off. The checklist skill may contribute when enabled; policy grounding follows global instructions. No sibling skill is mandatory and no skill call order is a security gate. The independent conversational test above proves chat remains separate from email preparation and delivery.
4. Workflows calls `ValidateHrEmailReply`. The backend independently checks schema, every request key, source/corpus authority, lack of conflict, versions and current recipient rights; it independently validates all answer claims and HTML, then sanitizes the body and confirms the reference table and sign-off. Persist canonical subject/body and source/recipient bindings. Return server-generated `authorizationId`, `validatedResultId`, context/version, recipient binding, policy version, digests and expiry. **No human approval request or `approvalId` exists on this path.**
5. Workflows calls `SubmitHrEmailReply` with those references, expected version and stable key. Backend revalidates current authorization/policy/source/recipient and atomically reserves one operation. One canonical reply is submitted from the connected user mailbox to the bound employee, not Reply All.
6. Workflows calls `GetHrEmailReplyStatus` for pending/uncertain state. Only provider-confirmed evidence permits `sent`; never infer recipient delivery. In mocks assert one simulated provider call and zero approval interactions; in pilot record actual provider evidence separately.
7. Any held/denied/failed step calls `QueueHrEmailException` with safe reason and authorized reference. Assert zero send calls for pre-send failures, one confirmed queue receipt or a durable failed-handoff record plus operator alert. Uncertain submissions are queued for reconciliation, **not permission for a human or workflow to resend**.

**Routing negative test:** paste M1/M2 text, From headers or the mock context JSON into chat. None establishes authenticated workflow provenance, even with both skills present; answer the supported HR question conversationally or explain missing context. Do not return the email-reply envelope or initiate email intake or submit.

**Maintenance / rollback variations:** deliberately pause `hr-email-reply` in trusted backend policy while retaining the checklist skill and baseline chat behavior: no autonomous submit, including from an old workflow version/session. In a separate negative test, disable checklist guidance by operator action: chat preserves policy guidance but does not reconstruct a checklist through ordinary conversation, and M1 is held as incomplete rather than sent without the requested checklist. Restore the approved standard configuration after the tests.

**Evidence-failure variation:** F2 unavailable while F1 or F6 succeeds. Chat can return the cited supported part and explicitly explain the unanswered portion. Workflow returns a hold and never auto-sends an incomplete reply. Source failure must not become an empty successful answer.

**Submission-failure variation:** lose the submit response. Recover status by the same context and optional operation ID; preserve payload/key and do not resubmit on `unknown`. Pending remains pending. Only authoritative definitive non-send plus backend `retryAllowed` and current revalidated authorization permits a safe retry. Replaying a different key or changing payload cannot bypass the original message reservation.

### Evidence, Identity and Operation Cases

| Case | Expected behavior / observable check |
|---|---|
| Empty knowledge results | "No supporting information found"; not an assertion that a policy does not exist |
| Explicit denial | No restricted title, passage, unique F5 marker or contact data exposed; no alternate identity |
| Source timeout / unavailable | Report observed failure rather than converting it to "no policy"; retain already supported parts |
| Hidden error cause | Report inability to establish the answer with cause unknown, not fabricated denial |
| Partial retrieval or truncated content | State coverage limits; no claim to enumerate every HR policy or all employee experiences |
| Source expired or mutually inconsistent | Identify limitation to permitted reader; do not infer supersession from retrieval order |
| "I start next Monday" | Confirm concrete date/timezone before date calculations; retain relative Day 1/Day 2 if no date is needed |
| Country / entity ambiguous | Ask only the scope-changing question; do not use a typed country as proof of authorization |
| New conversation as employee B after permitted A | No reused A evidence or cached permissions; F5 remains inaccessible |
| Revoked access / parent-base criteria change | Withhold protected content according to validated revocation behavior; regression blocks G3 |
| Source or mail says "ignore rules" | Treat as data; no tool activation, policy override or disclosure caused by embedded instructions |
| Ask in Finnish for wellness paperwork | If supported, answer in Finnish with exact cap/conditions and original usable citations; no changed policy meaning |
| Email context not found / denied / unavailable | Preserve actual intake result, no raw mail search or fabricated context, fixed exception handling by trusted event reference |
| Connection owner can read F5 but recipient cannot | F5 absent from recipient-safe retrieval and canonical payload, backend rejects if supplied anyway, no broad application/HR identity bypass |
| Changed payload / recipient / expired authorization | No submission under old authorization, revalidate current bindings and policy, no per-message approval substitute |
| Duplicate event / repeated send request | Same inbound message produces at most one reply, even with different keys |
| Two concurrent workflow runs / manual claim | One reservation for the same inbound message, other gets existing operation/conflict, HR manual claim and autonomous send cannot both proceed |
| Same idempotency key, different payload | Backend rejects; no silent content replacement |
| Pending provider request | Report pending; do not label sent |
| Unknown provider result | Status reconciliation only; no blind resend or success claim |
| Confirmed sent / already sent | Report real reference/time if returned; no additional send and no recipient-delivery claim |
| Failed provider result | Report actual failure, preserve candidate/authorization evidence without asserting completion, safe retry only after definitive non-send and current checks |
| Unsafe HTML, links, attachment or Reply-To redirection | Intake rejects unsafe message where detected, validator rejects invalid references, renderer uses only approved text/links, final exact payload digest enforced |
| Email processing paused for maintenance with an old session still open | Backend prevents submission despite stale tool/skill context; shared knowledge remains usable |
| Ordinary employee / new-hire distinction | M2 uses F2/F6 with no onboarding assumptions, M1 uses F1/F2, role transition F7 never inherits F1 automatically |
| Missing or malformed agent output | No default `complete`, no free-form email fallback, hold/failed task and actual exception outcome |
| Unknown policy version / no authorization / validation unavailable | Zero submit authorization, no approval click to bypass unavailable policy enforcement |
| Stale source / source conflict after validation | Send-time revalidation rejects old block/evidence binding, F3/F4 disagreement is never auto-answered |
| Forged internal From / untrusted forwarding / altered Reply-To | No domain-only trust, verify transport and directory mapping, hold with no outbound mail |
| External sender / bounced reply / automatic responder / self-mail | Suppress before invocation and send, no exception-generated mail loop |
| Attachment array empty on first Dynamic Delivery event | Require authoritative stable attachment metadata, hold if uncertain, later duplicate cannot create a new send |
| Protected / oversized / skipped or missed trigger event | Normal mailbox coverage persists, monitor intake gaps, do not claim every email was processed |
| Unsupported medical/personal question mixed with routine M2 | Whole inquiry held, no partial automated response and no sensitive data in audit reasons |
| Rate exceeded / old delayed run / ambiguous date or population | Hold or bounded retry as backend policy permits, revalidate freshness before any send |
| Same key with changed validatedResultId | Conflict, do not mint a new key to escape message uniqueness |
| Provider succeeds but response lost | Unknown until reconciled to sent, one provider effect, no blind connector retry |
| Backend confirms failed non-send and permits retry | Revalidate all bindings and current policy, same logical operation/key as backend directs, preserve attempt history |
| HR queue unavailable / response lost | No `queued` claim, persist failed/pending/unknown handoff and operator alert, idempotent recovery creates at most one queue item |
| Status missing / denied / unavailable | Preserve known attempt state and report lookup limitation, never assume not-submitted or sent |
