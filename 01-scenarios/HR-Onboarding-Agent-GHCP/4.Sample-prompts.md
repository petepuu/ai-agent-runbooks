# Sample Prompts — HR Onboarding Agent (GHCP)

These are acceptance cases, **not evidence of successful live tests**. All tenant and integration runs are not run. Use synthetic test content in an isolated source and never replace real HR policy with these fixtures.

## How to Use These Prompts

Use the prompts in Studio Preview first, then the authenticated Teams / Microsoft 365 Copilot pilot after channel validation. Test established employees as well as new hires. The baseline answers, builds onboarding checklist text and drafts replies in chat; it does **not** receive or send email. Autonomous-workflow tests start with isolated non-sending mocks, followed by a release-authorized real-mail pilot only after implementation and invocation gates pass.

Adapt applicability details such as cohort, country and timeframe without adding sensitive employee data. These short starter prompts are also suitable for the agent's suggested-prompts list:

- What does the approved employee handbook say about the code of conduct? Include sources.
- Make a first-week onboarding checklist from the applicable onboarding guidance.
- Summarize the available medical plans in a table; mark costs the sources do not specify.
- Draft a response to this HR inquiry using approved knowledge, but do not send it.
- I have worked here for five years. What is the published leave-request process?

### Example Email Interaction

> **Synthetic inquiry:** Subject "First week and wellness"; body asks for week-one tasks and wellness paperwork.  
> **Baseline expected result:** Subject and cited reply body in chat, labeled "Draft only - not saved to a mailbox or sent."

## Tips for Getting Better Responses

| Tip | Example |
|---|---|
| Provide only relevant applicability | "For cohort A, summarize the wellness policy." |
| Request an evidence-based format | "Use a table and mark information the sources do not specify." |
| Name the timeframe | "Make a first-week checklist; do not create tasks." |
| Keep drafting separate from sending | "Draft a reply, but do not send it." |
| Ask for the source of a claim | "Which current article supports that condition?" |

## Out-of-Scope Topics

Personal HR records, personal medical data, live leave balances, payroll/bank changes, benefit enrollment, leave submissions, HR case creation, provisioning, scheduling and task completion are excluded. General published benefits information is not a personal medical record. Arbitrary-recipient mail, Reply All, attachments, forwarding and autonomous replies outside the release-approved routine policy are excluded.

For unsupported questions, the expected response is an explicit evidence/scope limitation and the verified HR route when available. Do not invent a contact or claim a handoff occurred. The matrix's OFF capability state cannot be overridden by a prompt.

### Composed Scenario

**Chat request:** "For cohort A, explain wellness paperwork, make my first-week checklist, and draft a reply containing both. Do not send."

Expected **baseline** evidence/action sequence:

1. Confirm the three baseline capabilities are active. Reuse cohort A, no unnecessary identity or medical questions.
2. `hr-policy-answer` retrieves F2 from configured knowledge for the current permitted caller. Explain the receipt and short purpose statement; include the actual retrieved citation.
3. `hr-onboarding-checklist` retrieves F1 and emits exactly the three supported tasks with day/week timing and citation. Status is guidance, not completed.
4. `hr-email-draft` uses applicable evidence from this task or retrieves it again when necessary. Return subject, body, sources and gaps; label **Draft only - not saved to a mailbox or sent**.
5. End with no sending. Trace contains **zero** mailbox/backend calls. With autonomous-workflow enabled the same chat request still remains draft-only.

Expected **autonomous-workflow composed sequence**, using M1 to exercise policy, onboarding and reply preparation, then M2 for ordinary established-employee guidance:

1. Mock intake first, or the qualified Outlook shared-mailbox trigger in the release-authorized pilot, calls `AcceptHrEmailEvent`. Verify internal sender mapping, stable message identity, exact recipient binding, safe population/corpus and deterministic request match. Return the authoritative envelope/catalog and no existing reply.
2. Workflows invokes the **existing published HR GHCP agent** through the qualified Agent node, not through an agent-called workflow tool. Verify the target/version and effective identity. The agent uses permitted F2 policy evidence and F1 checklist evidence for M1, or F2/F6 policy evidence for M2. It must not retrieve broader service-identity content.
3. `hr-email-reply` returns exact structured block/evidence references. Policy/checklist skills may contribute reasoning when enabled; no sibling skill is mandatory and no skill call order is a security gate. The independent chat draft test above proves drafting remains separate from delivery.
4. Workflows calls `ValidateHrEmailReply`. The backend independently checks schema, every request key, source/corpus authority, lack of conflict, versions and current recipient rights; it renders exact approved blocks. Persist canonical subject/body and source/recipient bindings. Return server-generated `authorizationId`, `validatedResultId`, context/version, recipient binding, policy version, digests and expiry. **No human approval request or `approvalId` exists on this path.**
5. Workflows calls `SubmitHrEmailReply` with those references, expected version and stable key. Backend revalidates current authorization/policy/source/recipient and atomically reserves one operation. One canonical reply is submitted from the HR mailbox to the bound employee, not Reply All.
6. Workflows calls `GetHrEmailReplyStatus` for pending/uncertain state. Only provider-confirmed evidence permits `sent`; never infer recipient delivery. In mocks assert one simulated provider call and zero approval interactions; in pilot record actual provider evidence separately.
7. Any held/denied/failed step calls `QueueHrEmailException` with safe reason and authorized reference. Assert zero send calls for pre-send failures, one confirmed queue receipt or a durable failed-handoff record plus operator alert. Uncertain submissions are queued for reconciliation, **not permission for a human or workflow to resend**.

**OFF variations:** baseline receipt cannot invoke the email path. Disable `hr-email-reply` in trusted backend policy while retaining chat skills: no autonomous submit. Disable checklist guidance: chat preserves policy guidance but no checklist through a draft, and M1 is held as incomplete rather than sent without the requested checklist. Repeat after disablement with an old workflow version/session.

**Evidence-failure variation:** F2 unavailable while F1 or F6 succeeds. Chat can return the cited supported part and an explicitly partial draft. Workflow returns a hold and never auto-sends an incomplete reply. Source failure must not become an empty successful answer.

**Submission-failure variation:** lose the submit response. Recover status by the same context and optional operation ID; preserve payload/key and do not resubmit on `unknown`. Pending remains pending. Only authoritative definitive non-send plus backend `retryAllowed` and current revalidated authorization permits a safe retry. Replaying a different key or changing payload cannot bypass the original message reservation.
