# HR Onboarding Agent

## Overview

Employees often face challenges understanding company policies and accessing
necessary resources; new hires also need help integrating into the team. **HR Onboarding
Agent** uses the **GitHub Copilot harness in Microsoft Copilot Studio** for all
employees, with onboarding as a subset. This agent helps by:

- Answering HR-related questions using a ServiceNow knowledge base
- Automatically responding to routine policy-authorized inquiries sent to an HR shared mailbox, without per-message human approval
- Being accessible via Microsoft Teams and M365 Copilot
- Creating source-grounded onboarding checklists and draft-only email text in chat

Use one standard configuration with all four [runtime skills](0.Resources/Skills/README.md).
Email follows **email → Copilot Studio Workflows → existing published HR Onboarding Agent
→ same workflow → deterministic validation / Outlook reply → employee**. No send,
queue or mailbox tools are exposed to the agent. The five backend interfaces in the
[matrix](0.Resources/Capability-matrix.md#email-integration-contracts) require implementation;
these documents and skills are not a deployed solution.

Before starting, confirm the following are in place:

|---|---|---|
| Microsoft 365 Copilot access | Tenant admin verifies licensing and agent access for the intended channels | M365 Admin Center |
| Power Platform Developer Environment | Approved non-default development environment with Dataverse and GHCP availability; not a production hosting recommendation | Power Platform Admin Center |
| ServiceNow Developer Tenant | Free developer instance for knowledge base setup | developer.servicenow.com |
| GHCP authoring and capacity | Maker roles, approved generally available model, data policies, region and budget for build/test/evaluate/runtime | Copilot Studio and tenant administration |
| Knowledge and test identities | HR-approved content, permitted/denied/revoked employee accounts, scoped connector identity and actual workflow identity | HR, ServiceNow and M365 identity owners |
| Autonomous workflow integration | Implement all five backend contracts, recipient-safe retrieval, grounded-answer and HTML validation, fixed HR exception queue and provider reconciliation | Workflows, backend and mailbox integration owners |

Assign HR content, identity, integration, privacy, test, release and cost owners.
Record actual configuration securely; never put passwords, tokens or connection secrets in Git.

### Step 2-3. Add Workflow for autonomous trigger

Use [Copilot Studio Workflows](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/flows-overview) and its [Agent node](https://learn.microsoft.com/en-us/microsoft-copilot-studio/workflows-experience/agent-node-workflow), **not a direct standard-harness agent trigger**. Direct triggers are anticipated for a later GHCP harness update; availability and timing are not confirmed in the [current event-trigger documentation](https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-trigger-event). This walkthrough uses Workflows.

1. Select **Workflows** from the left menu. If the agent has unsaved changes, click **Save and continue**.

> ![Select Workflows from the left menu](0.Resources/Images/067.png?v=7a6ad63354fc)

2. Select **New workflow**.

> ![Create a new workflow](0.Resources/Images/068.png?v=80df2b1cb0a5)

3. Select the **Start** (trigger) node and change **Trigger type** to **Connector**.

> ![Change the trigger type to Connector](0.Resources/Images/070.png?v=46bfe700fbaa)

4. Select **Office 365 Outlook**.

> ![Select the Office 365 Outlook connector](0.Resources/Images/069.png?v=866f983b56b2)

5. Select **When a new email arrives in a shared mailbox**.

> ![Select the shared-mailbox email trigger](0.Resources/Images/066.png?v=edac3435379d)

6. Configure the shared-mailbox V2 trigger (`SharedMailboxOnNewEmailV2`). Set its **Original Mailbox Address** and actual folder; verify delegated connection access. A Microsoft 365 group is not a shared mailbox.
7. Set **Include Attachments = No**. Backend intake still checks authoritative attachment metadata; this switch does not reject attached mail. Validate transport authenticity, employee mapping, stable message identity, rate/loop suppression and full request coverage through `AcceptHrEmailEvent`.
8. Add **Agent** from the designer's Add panel → **An existing agent** → select the published **HR Onboarding Agent**. Do not create an inline agent or substitute an unverified Execute Agent connector route.
9. In **Message**, supply the sanitized inquiry and isolated trusted context and allowed topics from accepted intake. Record exact GHCP target/version, imported skill execution and effective retrieval identity. Keep **Request human assistance when unsure** disabled; exceptions use the fixed HR queue, not email to the connection owner.

10. In the **same workflow**, parse the returned candidate as untrusted data. Run `ValidateHrEmailReply`, then `SubmitHrEmailReply` **only** on an authorized server result, using its `authorizationId` and `validatedResultId`. Send only the validated, sanitized HTML body bound by the backend; never accept model-provided recipients or authorization.
11. Route held/failed/malformed results to `QueueHrEmailException`, and pending/unknown submissions to `GetHrEmailReplyStatus`. Inspect every branch, retry setting and version before saving. Routine authorized replies need no per-message human approval.

12. Keep send credentials physically absent or revoked during isolated testing. Workflow node tests can call real APIs; mock input alone is not isolation. Activate the approved real-mail pilot only after E1–E2/D3 pass and release/mailbox owners authorize it. Native Email is unavailable in the [GHCP channel table](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/publication-channels-overview); this workflow supplies the email entry path.

### Step 4-4. Monitor and Roll Back

Use **Monitor**, workflow Activity and backend telemetry. Track knowledge/permission failures,
policy validation, provider status, queue receipts, failed handoffs, missed intake and credits.
On regression, stop intake/submission and revoke backend authorization; reconcile pending/unknown
attempts without resending. Withdraw the affected audience or restore a recorded known-good
configuration and republish. Keep necessary shared knowledge and scoped status access.
