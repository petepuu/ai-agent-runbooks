Delivered assets are documentation, runtime definitions, synthetic fixtures and an unmanaged solution package for development and test. No deployed agent, connection, service credentials, real invoice data or successful tenant test evidence is included, and importing the package closes no release gate. Keep operational evidence and environment values in the organization's access-controlled delivery record.

Import the ready-made solution as described in [5. Working Solution](../5.Working-solution.md), or build in this order: the SharePoint library, then the Dataverse solution, table and environment variables ([Runbook Step 2-2](../3.Runbook.md#step-2-2-create-table) has the Copilot prompt that creates the **Auto Invoice Review** table), then the agent with its tools, instructions and skill ([Runbook Step 3-1](../3.Runbook.md#step-3-1-create-the-agent)), then the two workflows, then the tests. The [Runbook](../3.Runbook.md) has the steps. Uploading a skill does not create tools, connections, the workflows or any authorization. Copilot creates the intake workflow from the ready-made prompt in [Runbook Step 3-3](../3.Runbook.md#step-3-3-build-the-intake-workflow-invoice-intake) and the approval workflow from the one in [Runbook Step 3-4](../3.Runbook.md#step-3-4-build-the-approval-workflow-invoice-approval). Turn on the approval workflow before the intake workflow. The decision check, the approval and the emails live in the approval workflow, not in a skill.

## Release gates

Each gate is closed by its named role before dependent behavior is enabled. These are implementation requirements, not optional capabilities.

| Gate | Owner | Required evidence / acceptance |
|---|---|---|
| G1 — Host, PDF reading and tool identity | Delivery engineer / Power Platform admin | [VERIFY] The agent uses the GitHub Copilot harness. A tool-returned PDF from the SharePoint tool is read correctly for a text invoice and a scanned invoice. The agent has the `CreateFile`, `CreateSharingLink` and `GetMyProfile` tools under the names the skill uses. In Preview, a PDF uploaded in the chat is saved by `CreateFile` to `/Invoices/Sources` under its own name, `GetMyProfile` returns the Object ID of the person who is chatting and not that of the connection owner (it can fail for guest users, and then Submitted By is empty), and the agent answers with a table of the extracted values and a short summary of the invoice. The tool connections used in workflow-invoked runs are the intended service account with only the permissions in the [matrix](Capability-matrix.md#agent-tool-contracts) |
| G2 — Workflow-to-agent call | Delivery engineer | [VERIFY] The Agent node in the intake workflow can select the published agent, send the prompt and wait for the finish, with the default text output that nothing reads. What happens when the agent step fails is recorded, including whether the intake run still ends as succeeded when the agent wrote no row. The prompt carries the email subject and the sender's Object ID but no link, so record what `invoice-extraction-review` writes into `emailSubject`, `submittedBy` and the Submitted By column, and whether the Source Link and Review Link columns are filled. Record whether a failed PDF stops the loop |
| G3 — Approval and run failures | Power Platform admin / AP approver | [VERIFY] The approval action is available in the approval workflow, the approval time limit and run duration suit the approver's response time, and a failed run of either workflow alerts the owner. The manager lookup returns the manager of the submitter, found by Object ID, and for a submitter without a manager, outside the organization or with an empty Submitted By it returns nothing or fails without stopping the run, so the approval goes to the `FinanceEmailAddress` value. The submitter lookup in the approval workflow and the sender lookup in the intake workflow (Office 365 Users **Get user profile (V2)**) accept an Object ID and an email address respectively, and a failed or empty lookup does not stop the run. The approval returns the outcome values that the **Approved** (`Approve`) and **Rejected** (`Reject`) conditions test, and any other outcome takes the **Other** branch |
| G4 — Dataverse behavior | Dataverse owner | [VERIFY] 18 columns saved as specified, no column is required, and the sample rows are deleted. The invoice number from the skill's `InvoiceNumber` field lands in the Invoice Number column, and the Object ID lands in Submitted By. A row is still created when the primary name column is empty. Choice labels can be written. Decimal precision 2 is kept. The Dataverse tool can create a row and read the `environmentvariabledefinition` and `environmentvariablevalue` tables. The Workflows experience offers the Dataverse **When a row is added, modified or deleted** trigger and the **Get a row by ID** action, and the connection owner has the rights on the **Callback Registration** table. A row created by the agent's Dataverse connection is owned by that account, so the trigger at scope User starts when the same account owns the approval workflow. The `Invoice` step returns the Decision as the label `READY_FOR_APPROVAL`, or the number, and the date and decimal values arrive in a usable form |
| G5 — Mailbox and SharePoint behavior | Messaging owner / SharePoint owner | [VERIFY] The trigger fires for the invoice mailbox and skips oversize or protected mail as documented. Send rights for the Finance and submitter emails work for the mailbox type. Create file behavior when a name exists is recorded, and so is a review file name that holds a character SharePoint does not allow. The tool's accepted path form, the item ID that `CreateFile` returns for the uploaded PDF and for the review file, and the sharing link properties are recorded, how the `SharePointDocumentLibrary` and `SourceFolderPath` values combine into the Create file folder path is recorded, and a sharing link fits in 200 characters. The two folders exist and are permissioned. The intake workflow can read its three environment variables and the approval workflow can read `FinanceEmailAddress` |
| G6 — Business configuration | AP/Finance owner | [FILL] Invoice mailbox, optional sender allowlist, the Finance address in `FinanceEmailAddress` (also the approver when the submitter has no manager), files-per-email cap, retention and the site, library and folder values in the environment variables |
| G7 — Test evidence | Test / privacy owner | [VERIFY] The [smoke path](../4.Sample-prompts.md#smoke-path) passes first, that is the checks of [Runbook Step 4-1 and Step 4-2](../3.Runbook.md#phase-4-testing): a PDF uploaded in the Preview chat, then both workflows with an invoice that is approved, one that is rejected, an invoice with missing information that goes to Finance with the submitter in CC, and a missing `FinanceEmailAddress` value. Then every other case in [Sample Prompts](../4.Sample-prompts.md#acceptance-cases) is run in isolation, followed by the composed run, with the result and evidence recorded. The test rows and test files are deleted afterwards. No real invoices are used before the pilot is approved |
| G8 — Cost and capacity | Release / cost owner | [VERIFY] Credit use for a measured number of invoices, expected monthly volume and budget controls. SharePoint call limits are not exceeded at peak volume |
| G9 — ALM and rollback | Power Platform engineer | [VERIFY] The solution moves from Dev to Test to Prod, the connections are rebound, the skill versions are traceable and the rollback steps are rehearsed |

Do not reduce a gate to an instruction telling the model to be careful. The decision check, the approval and the emails are deterministic steps of the approval workflow. The agent's instructions help it extract well, but they do not decide who is notified or who approves.

## Design choices and operational records

- Two workflows and one agent. The intake workflow calls the agent and ends there. A user can also upload an invoice in a chat with the agent in Copilot Studio, and the agent is not published to Teams, Microsoft 365 Copilot or any other end-user channel. The agent calls no workflow and has no email or approval tool. The Dataverse row that the agent writes is the only link to the approval workflow.
- The approval workflow decides from the row's Decision. The approval starts only when Decision is `READY_FOR_APPROVAL`, which the skill sets only when all 11 invoice fields were found. Any other Decision sends a manual review email to Finance with the submitter in CC. This is a **scenario-defined contract**.
- Every row that is added to the table and owned by the approval workflow's owner starts the approval workflow, including rows from tests and rows that the owner adds by hand. Keep it off while you test the agent.
- Routine intake has no per-message human approval before the extraction and the row are written. A person approves each invoice that is ready for approval, and the submitter gets an approved or rejected email afterwards.
- Record the invoice mailbox, approver, connection owners, library and solution names, tool and skill versions, test runs and release approvals in a restricted delivery record. Store no credentials or real invoices in this repository.
