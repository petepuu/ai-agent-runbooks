# Employee Self-Service Agent with Microsoft Copilot Harness - Scope and Readiness

> **Deliverable**: Source/integration inventory, prioritized use-case backlog and example planning workbook. Not a configured or deployed agent.

Complete this planning stage before implementation. Configuration guidance continues in the [runbook's knowledge phase](4.Runbook.md#phase-1-configure-knowledge) and [optional live integrations phase](4.Runbook.md#phase-2-implement-optional-live-integrations).

## Phase 0: Scope and readiness

### Step 1: Define knowledge sources and external system integrations

Start by identifying the information employees need and the systems that own it. This scenario supports **ServiceNow and Workday external system integrations**, plus approved **SharePoint and ServiceNow knowledge**. Select only the sources and integrations needed for the planned scope; support in this blueprint does not mean a connection or live tool is already available.

Keep knowledge retrieval separate from live reads and writes. A ServiceNow Copilot (Graph) connector indexes approved knowledge; it does not authorize incident or HR case operations. Personal Workday records are accessed only through separately approved live tools, never indexed as knowledge.

Use the following candidate inventory and the **Sources and integrations** sheet in the [example planning workbook](0.Resources/Use-case-planning.xlsx).

| Source ID | Source / system | Information or operations needed | Access path to plan | Boundary / owner |
|---|---|---|---|---|
| SRC01 | ServiceNow knowledge | Published HR and IT KB articles | ServiceNow Microsoft 365 Copilot (Graph) connector and configured knowledge retrieval; see Phase 1 | Article/KB user criteria and employee retrieval permissions; knowledge + ServiceNow owners |
| SRC02 | SharePoint knowledge | Approved HR policies and IT guidance | Configured SharePoint knowledge; see Phase 1 | Library/document permissions, country, language and effective date; knowledge owners |
| SRC03 | ServiceNow ITSM | Own incidents: create, list, details, latest updates, update and attachments | Separately enabled delegated tools; Microsoft Entra ID user mapping; see Phase 2 | Incident management only, own-record and allowed-field enforcement; IT + ServiceNow + identity owners |
| SRC04 | ServiceNow HRSD | Own HR cases: create, list, details, latest updates, update and attachments | Separately enabled delegated tools; Microsoft Entra ID user mapping; see Phase 2 | Own employee-visible cases; sensitive matters use the approved human route; HR + ServiceNow + identity owners |
| SRC05 | Workday | Own employee information; optional email and phone updates | Supported delegated MCP/workflow path, Entra SSO and employee identity mapping to validate; see Phase 2 | Per-capability domain permissions and HR/privacy approvals; HR + Workday + identity owners |

For each selected row, record the exact knowledge libraries/KBs or record types and fields, intended users/countries/languages, source owner, freshness needs, access restrictions, integration/authentication approach, dependencies and readiness gaps. Store environment URLs, connection IDs and other tenant-specific details only in the restricted deployment record. Mark unused rows **not selected**; mark an unavailable required integration **blocked**, not implicitly available.

### Step 2: Plan, list and prioritize scenarios and use cases

With the candidate inventory defined, group employee needs into scenarios such as IT self-service and HR self-service, then create one row per independently testable use case. Map each row to its source IDs and exact [capability IDs](0.Resources/Capability-matrix.md). Refine the source inventory if this planning exposes missing information or dependencies.

Capture the six fields shown below: **use case name, description, interaction, data source, success criteria and metric**. Also record priority and rationale, business value, demand/current baseline, delivery effort, owner, audience, capability dependencies, access/approval boundaries, readiness and proposed release wave. Use the workbook's **Use cases** sheet for the full planning record.

The rows, priorities and metric targets below are **illustrative examples**, not approved requirements or measured results. Confirm targets and measurement methods with HR/IT and QA before delivery. Unlike a generic ticket backlog, this scenario covers only own IT incidents and HR cases, not catalog requests or arbitrary ticket transitions.

| Use case name | Description | Interaction | Data source | Success criteria | Metric / example target | Example priority |
|---|---|---|---|---|---|---|
| UC01 - Retrieve ServiceNow knowledge | Answer employee HR/IT questions with contextualized, cited KB guidance | Knowledge retrieval | SRC01 - ServiceNow KB via Copilot (Graph) connector | Correct, permission-trimmed citations; faster useful answers | Citation accuracy >=95%; CSAT >=4/5; SUS >=70; median time-to-first-useful-answer vs baseline | P1 |
| UC02 - Find applicable HR policy | Find the approved policy for the employee's country and effective date | Knowledge retrieval | SRC02 - SharePoint policy libraries | Applicable, current policy cited without personal entitlement calculation | Correct applicable-policy citations >=95%; median time-to-find-policy vs baseline | P1 |
| UC03 - Check own IT incident status | Retrieve current status and latest employee-visible updates in chat | Task (read) | SRC03 - Live ServiceNow incident records | Correct own-record status; fewer status-check contacts | Status-query correctness >=95%; status-check contacts vs baseline; median time-to-status | P2 |
| UC04 - Create own IT incident | Preview and confirm an incident with the complete problem description | Task (write) | SRC03 - Live ServiceNow incident records | Confirmed payload persists; retries do not duplicate incidents | Payload match on verified creates 100%; duplicate incidents in retry tests 0; create success/error rate | P3 |
| UC05 - Update own IT incident | Add a confirmed comment or make a separately permitted state change | Task (write) | SRC03 - Live ServiceNow incident records | Only allowed fields/transitions change; actual outcome verified | Payload match on verified updates 100%; unauthorized transitions 0; update success/error rate | P3 |
| UC06 - Check own HR case status | Retrieve current HR case status and employee-visible updates | Task (read) | SRC04 - Live ServiceNow HR case records | Correct own-case answer; no internal notes or other employees' cases | Status-query correctness >=95%; cross-user disclosures 0; median time-to-status | P2 |
| UC07 - Read own employment information | Retrieve the employee's allowlisted employment details | Task (read) | SRC05 - Live Workday employee records | Correct, minimal own-record information | Allowed-field answer accuracy >=95%; cross-user disclosures 0; median time-to-answer | P2 |
| UC08 - Update own email contact | Select an existing contact record/type, preview and confirm the exact change | Task (write) | SRC05 - Live Workday contact records | Exact confirmed change read back; pending work never reported as complete | Payload match on verified completed updates 100%; false completion claims 0; update success/error rate | P3 |

Prioritize with business value and demand first, then source/integration readiness, delivery effort, dependencies and privacy/write risk. **P1** is the knowledge-only baseline; **P2** is a candidate live-read wave; **P3** is a candidate confirmed-write wave. These are example planning priorities, not permission grants or automatic deployment order. A high-value but blocked use case remains blocked until its gates pass. Do not relax ownership, confirmation or other hard boundaries to meet an example KPI.

Split composed journeys into their independently enabled capabilities and record the sequence and disabled/failed-step behavior using the [sample prompts and acceptance cases](5.Sample-prompts.md). For example, checking incident status can require list, details and latest-update capabilities; knowledge retrieval cannot substitute for any of these. Review and approve the backlog with HR, IT, knowledge and integration owners before configuration work.

### Step 3: Confirm scope, ownership and readiness

1. Keep the original scenario and existing agent/portal paths intact. Plan a new standalone Microsoft Copilot Harness agent.
2. Name HR, IT, knowledge, ServiceNow, Workday, identity/security, privacy, QA, release and cost owners. Store names and tenant values in a restricted deployment record.
3. Confirm employee-only HR/IT scope, representative countries/languages and intended Microsoft 365 Copilot/Teams audience. Baseline the top 25 question categories and current resolution time/ticket volumes before delivery.
4. Choose the knowledge-only baseline first. Use the approved backlog to select live capabilities individually from the [matrix](0.Resources/Capability-matrix.md); leave everything else OFF in backend policy and tool exposure.
5. Confirm the target Microsoft Copilot Harness environment, approved model, Entra authentication, DLP, region/cloud, channel availability, transcript retention, memory policy and current billing. Building, testing, evaluating and using the agent can consume Copilot Credits; do not inherit source seat thresholds or prices.
6. Resolve the [release gates](4.Runbook.md#release-gates) for the selected scope. A knowledge-only release may defer transaction gates only with those capabilities OFF and scope communicated honestly.

**Phase 0 exit:** approved source/integration inventory and prioritized use-case backlog, agreed metrics/baselines and owners, proposed release waves, selected capability manifest and explicit blockers. Completing the example workbook does not configure or enable an integration.
